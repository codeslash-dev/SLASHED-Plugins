## Executive summary

- **1 Critical, 4 High, 14 Medium, 18 Low** findings (37 total).
- **Critical (PL-025):** `.github/workflows/framework-sync.yml` runs `npm run check`, which does not exist anywhere in the root `package.json` script list (verified independently). This workflow fails on every run. Two independent parts of the repo — the CI workflow and the developer-facing docs (`README.md:74`, `CONTRIBUTING.md:34`) — reference a script that was apparently removed or renamed without updating either reference.
- **High (PL-023, verified):** `SLASHED-for-WP/assets/admin-app/app.js` (7360 lines) and `app.css` are compiled Vite/Svelte build output committed directly to `main`, with 35 commits touching `app.js` in the last 6 months alone — every configurator UI change produces a full-diff rewrite of a machine-generated bundle in PR history. Committing built assets is a defensible pattern for a WP-plugin release model (see "looks bad but fine"), but the churn volume is a real cost.
- **High (PL-006/PL-034, merged view):** There is effectively **zero automated test coverage** of the PHP backend (`includes/`, ~5000 lines: REST endpoints, CSS generation, token persistence, capability checks) and the one browser test that exists for the admin SPA (`tests/playwright-admin.js`) isn't wired into `npm test` or CI at all — it's dead weight that looks like coverage but provides none.
- **High (PL-013, verified):** A real behavioral bug from silent drift — the color-classification logic (`classifyVar`/`classify_color`) exists in three near-identical implementations (Bricks JS, Gutenberg JS, Gutenberg PHP). Gutenberg's JS correctly filters both `-light` and `-dark` source-duplicate tokens; **Bricks' JS and Gutenberg's PHP only filter `-light`** — verified by direct code comparison. Bricks' color picker will render a spurious duplicate swatch for every `-dark` token that Gutenberg correctly hides.
- The PHP backend's input-sanitization discipline is unusually thorough for a WP plugin (regex allowlists, balanced-paren checks, reserved-word blocklists, capability checks on every REST route) — flagged explicitly as a strength, not a gap.
- `readme.txt` states `Tested up to: 7.0` (PL-009) — plausible-but-unverifiable given the fictional-forward audit date; flagged as a question for the maintainer rather than asserted as an error.
- Two independent findings (PL-025, PL-036) both trace to the same root cause — a missing `npm run check` script — discovered from different angles (CI workflow failure vs. stale developer docs). Merged into one finding below.

## Architectural mental model

This repo packages the SLASHED CSS framework as a WordPress plugin with three integration surfaces: a general admin SPA (`admin-app/`, mostly vendored from the framework's own configurator), a Bricks Builder panel (`integrations/bricks/`, independent Svelte app + PHP glue, not vendored), and a Gutenberg integration (`integrations/gutenberg/`, framework-free vanilla JS + PHP using native `wp_localize_script`/theme.json mechanisms — appropriately lighter-weight than Bricks' full SPA). `includes/` is the shared PHP backend: REST API, CSS bundle generation/parsing, token persistence, and color-math resolution, all gated by WordPress capability checks. The plugin ships as a downloadable GitHub-release zip (not WP.org SVN), which is why built JS/CSS assets are committed to `main` rather than to a separate `dist` branch the way the framework repo does. A daily-cron GitHub Action (`framework-sync.yml`) is meant to detect drift against the upstream framework and PR the result — but per PL-025, that workflow is currently broken.

## Things that look bad but are actually fine

- **`SLASHED-for-WP/dist/*.css` and `assets/admin-app/app.js` committed to `main`.** This plugin ships as a downloadable GitHub-release zip, not via WP.org SVN — there's no `.org` deploy step in any workflow. Since there's no build step at install time for end users, committing built output to the tree that gets tagged and zipped is a defensible, common WP-plugin pattern, not an oversight. `.gitignore:11-13` explicitly documents the distinction between root `/dist/` (ignored, build-tool output) and `SLASHED-for-WP/dist/*.css` (tracked, shipped local-first CSS) with a clear comment. The *frequency* of `app.js` churn (PL-023) is the real cost, not the practice itself.
- **`sync-core.mjs`'s GitHub-API 403/404 fallback to "keep vendored copy."** Initially looks like silently swallowing errors, but it's a deliberate, commented rate-limit mitigation so unauthenticated CI runs degrade gracefully instead of hard-failing over GitHub API limits. The edge case in PL-027 (can't distinguish 404 from 403) is real but the overall design choice is sound.
- **Zero `WP_Error` usage across `includes/` (PL-002).** Looks like inconsistent error handling at first, but every failure path in this module is a legitimate "fall back to safe default" case (empty inventory, empty override map) rather than one that needs to propagate a rejection to a human, except the one REST case actually flagged.
- **876-line `class-color-resolver.php`.** Long, but it's pure computation (no I/O, no WP hooks, no direct user input — it only receives already-validated values from `Slashed_Token_Store`). Line count here is math tables (steps/aliases), not tangled control flow.
- **`class-css-parser.php` and `class-inventory.php` "duplicating" CSS logic.** On inspection this is a clean separation (pure regex parser vs. disk/cache/fallback orchestration) — each has exactly one reason to change, despite looking like duplication from file names alone.
- **The `--sf-*` regex allowlist appearing in both `class-rest-controller.php:293` and `class-css-generator.php:34,95`.** Looks like copy-paste drift risk, but the generator's docblock explicitly documents this as intentional defense-in-depth re-validation against a hypothetical future writer bypassing the REST layer — not accidental duplication.
- **Bricks and Gutenberg integrations diverging in tooling (Svelte SPA vs. framework-free vanilla JS).** Not inconsistency — Bricks' editor panel is a real SPA mounted in builder chrome (justifies the build step); Gutenberg's panel is a small overlay injected into existing WP admin markup, deliberately framework-free per its own header comment. Appropriately different scale of UI, appropriately different tooling.
- **Gutenberg having zero REST routes while Bricks has two.** Gutenberg's editor integration works entirely through `wp_localize_script` + native `theme.json`/`add_theme_support` filters — the idiomatic WP mechanism for block-editor presets. No REST endpoint is architecturally needed for that use case.
- **`data/inventory.json` existing in two places (`SLASHED-for-WP/data/` and `integrations/bricks/data/`).** Looks like a drift risk, but both are generated from one source by `scripts/gen-bricks-inventory.js`, and `scripts/verify-sync.js` hashes both and fails CI if they differ. Solved problem.
- **`phpcs.xml.dist` disabling `Generic.CodeAnalysis.UnusedFunctionParameter`.** Looks like laxness, but the justification (WP hook callbacks must keep full signatures even when unused) is a legitimate, well-known WordPress-specific false-positive pattern.
